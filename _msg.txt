Wait for the bot's actual reply instead of sleeping a fixed 3 seconds

A live run added 53,412 numbers successfully but reported the wrong result:
the first file's outcome was shown as the /useddelete reply ("Deleted 4,796
used/expired numbers") rather than its own confirmation. Cause: the code
slept 3s and then read the latest bot message. A large file takes the target
bot far longer than that to ingest, so the read returned the PREVIOUS
message - the automation had no way to tell "it answered" from "it has not
answered yet".

Both the add and the quota check now anchor on the id of the last bot
message before sending, then poll until something newer appears (90s for an
add, 45s for a quota check). No reply within the window is now an explicit
failure that says the add may or may not have gone through, instead of
silently attributing someone else's message to this file.

Test doubles updated to issue increasing message ids, since "newer than what
I last saw" is now the thing under test; FailingUserbot gained the methods
the real path touches first. Two regressions added: one drives a bot that
only answers after several polls and asserts the stale /useddelete text is
never reported as the add's result, another asserts a silent bot fails
loudly and leaves nothing marked active.

600 tests (was 598), smoke 10/10.
