Per-country on/off and a wall-clock stop time, in Dubai time

Turning one country off meant deleting it and losing its file; stopping at a
particular hour was not expressible at all - only "after N minutes", which
is what ended an overnight run three minutes after it began.

Pause / resume per country
  set_paused keeps the file, the tag and every setting and simply skips the
  country until it is resumed. Distinct from removal, which throws the file
  away. A paused country's timer is not advanced while it is off, and
  resuming re-arms from now, so a country paused for hours does not fire the
  instant it comes back just because its old due time went by.

Stop at a time of day
  stop_at is a wall-clock "HH:MM" in Dubai time, stored as a string rather
  than a timestamp so "stop at 23:30" keeps meaning 23:30 on whatever day
  the run is still going, instead of expiring after the first night.

  It is compared against the run's START, not against "today": a run begun
  at 22:00 with a 01:00 stop ends at 01:00 the NEXT day. Comparing to today
  would finish an overnight run immediately - the exact case this is for.

  Dubai is UTC+4 year-round, so a fixed offset is exact and needs no tzdata
  in the container.

Show the clock
  The server thinks in UTC, the owner reads Dubai time, and a stop time
  picked against the wrong one is four hours out. Both are now shown
  wherever a time is chosen: the Telegram settings list, the stop-time
  prompt, and above the web schedule table.

  Input is forgiving ("2330", "23.30", "9:05") but validated - "25:00"
  stored unvalidated would simply never fire and look like a broken
  feature. The web form posts free text, so it goes through the same
  validation as the chat command rather than trusting the browser.

Both UIs: Telegram gets a country on/off picker, per-country off/remove
buttons and a stop-time keyboard (six common times, custom, or never); the
web schedule table gets a Turn on/off button and a time field per row.
