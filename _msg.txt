OTP-bot: multi-file queue, autonomous tags, start/stop, notifications

The owner's actual workflow: send several number files one at a time, say
"start" or "done" once, and the agent should take it from there with as
little back-and-forth as possible - deciding things itself instead of
asking every time.

app/automation/otp_bot.py: files now go into a persistent QUEUE on upload
(Telegram or web). Before ever prompting for a tag, the agent tries to
decide it on its own: read it straight off the filename if it contains a
known region/campaign token (numbers_BD_batch2.txt -> "BD"), fall back to
an owner-configured default_tag, then fall back to whatever tag was used
last time (the common case: same campaign, new batch). It only asks when
none of those give an answer, and even then asks once per file, not once
per message.

start()/stop() replace the old single always-on config: "start"/"done"
(or the Start button) sends /useddelete once, then adds every queued file
as its own reply-to-file-message command (still required by the target
bot's FSM) with its own tag, and only then turns the periodic quota
monitor on. "stop"/"off" just pauses the monitor - queue and the files
that were actually added stay recorded, so resuming later is a clean,
explicit decision, and if the owner says "start" again with nothing newly
queued the agent resumes the same files on its own rather than asking
which ones. A bot reply that looks like a rejection ("No valid phone
numbers found", etc.) is now treated as a real failure, not silently
reported as success.

These triggers are matched deterministically in app/agent/conversation.py
BEFORE the LLM router runs, so "start"/"stop"/a bare tag answer work
identically from Telegram or the web dashboard chat even while every LLM
provider is down - the same reason this whole module avoids the LLM in
the first place.

Web dashboard OTP Bot panel: separate Queue and Active-files views, Start/
Stop buttons, per-file tag input, plus the existing settings (target bot,
interval, threshold, commands) now including a "default tag" field. /otpbot
on Telegram is now a read-only status/quick-override view that also shows
queue + active file names; the real day-to-day flow needs no command syntax
at all. Telegram gets a push notification whenever start/stop actually
fires, regardless of which channel triggered it.

591 tests (was 573; rewrote test_otp_bot_automation.py's 6 tests into 20
covering tag inference/default/reuse, queue lifecycle, bot-rejection
handling, and the deterministic start/stop/resume triggers; added 7 more:
2 API queue-endpoint tests, 3 conversation-trigger integration tests, plus
schema doc updates), smoke 10/10.
