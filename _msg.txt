Quota check: accept only a reply that is actually a quota

Live "check quota now" failed with "could not parse an 'Active' count",
quoting the bot's own "Fast Add Complete!" notice. Waiting for a NEWER
message was not enough - the target bot posts its own progress and
completion notices, so a stray one arrives first and gets mistaken for the
answer while the real /myquota reply is still in flight.

_wait_for_new_bot_reply now takes an optional predicate, and the quota
check only accepts a message that actually parses as a quota; anything else
newer is skipped and the wait continues. Unparseable chatter is therefore
"not the answer yet" rather than a hard failure, which is what it always
meant.

The parser also now accepts comma-grouped counts ("Active : 4,796"), which
appear once the number grows and would otherwise have read as unparseable.

Tests: the real reply formats are pinned (including the grouped-thousands
case and a "Fast Add Complete!" line that must NOT parse), plus a bot that
posts an add notice before its quota reply and must still be read
correctly. The old unparseable-quota test asserted the now-obsolete
behaviour and was rewritten to match what the code should do.

602 tests (was 600).
