Uploads start themselves, and stop cancelling the runs already going

Three problems, all on the path between "owner drops a file" and "numbers
are actually in the bot".

A new upload cancelled everything already running
  start_automation wrote the queue over the active set. Uploading a Nigeria
  file therefore silently ended the Bangladesh run started an hour earlier -
  the countries simply disappeared from the active list with no message.
  The active set is now MERGED: countries not in the new upload keep
  running, and a new file for a country already running supersedes that
  country's entry only, rather than being added alongside it as a duplicate.

Uploading meant nothing until "start" was typed
  A file dropped in the OTP thread is a request to run it; asking "shall I
  start?" afterwards is a question whose answer is always yes. An upload now
  starts by itself, from both Telegram and the web dashboard.

  The one case that still asks is a file whose tag is unknown - starting
  with a guessed tag would file the numbers under the wrong service, which
  is not recoverable from this side. That path already auto-started from the
  tag answer, so the question is asked once and the run follows immediately.
  Switch the whole behaviour off with auto_start.

Re-adding numbers a country already had
  Adding a file to a country that is already stocked produces nothing but
  duplicates (live: 46,588 of them) and burns the file. Start now reads the
  bot's own /st once, up front, and holds back any country whose stock is
  above its restock point - the file stays queued and the country stays
  monitored, so it goes in the moment it actually runs out.

  A country's own restock point is used, not a global one, so a country set
  to refill at 200 is topped up at 200 here too.

  If the stock read fails the add proceeds anyway: the worst case is
  duplicates, whereas refusing to start is a dead automation. The cleanup
  command is skipped entirely when nothing is going to be added, so a start
  that holds every file leaves no trace in the chat.

  Held files are reported as held, with the current stock and "auto add
  hobe" - "ignored" and "held" look identical otherwise.

format_start_result and tag_question are public wrappers so the Telegram and
API upload handlers stop reaching for the private helpers.

Two existing tests turn the new pre-check off: they assert the exact message
sequence of an add, which now legitimately begins with /st.

748 passing, smoke 10/10.
